# TEST-REPORT-0.6.0 —— 自动压缩督导三项评估（模型性能 / 成本 / 稳定性）

> 日期：2026-10-16 凌晨 · 对象：wb-ops 0.6.0（ctx-guard v2 + PreCompact）· 方式：独立新会话复评（非实施会话）  
> 前置文档：`AUTO-COMPACT-FEASIBILITY.md`（宿主压缩机制、触发点、介入通道的完整调研）  
> 结论先行：**不会降低模型性能**（常规轮零感知，压缩路径三重质量保护）；**成本**单次压缩回收 ~106K token、重型会话输入重放 -81%；**稳定性** 398 项测试全绿、三层一致、实机生效。

## 〇、对象与部署核验

- 0.6.0 内容：ctx-guard v2（UserPromptSubmit：行为学习 / 双档提醒 / 压缩后检查）+ PreCompact（压缩保留清单注入）。
- 三层 md5 一致（dev = 市场副本 = cache/0.6.0）：ctx-guard `6e70e888`、precompact `8f624c02`、hooks.json `3c6d5ef3`；plugin.json 与注册表均指向 0.6.0。
- 实机生效实证：宿主日志显示，独立的评估会话 00:01:51 的 UserPromptSubmit 由 `cache/local/wb-ops/0.6.0/hooks/ctx-guard.mjs` 实际执行（5s 超时内、零输出静默）；SessionStart 记忆守卫同为 0.6.0。
- 宿主压缩机制（背景）：deepseek-v4.1-flash（官方 300K）自动压缩触发点 150K；gpt-6.1-sol（自定义）固定 200K；压缩保留 `cb_summary` + 最近 5 轮原文（两级压缩：工程压缩免费 → 不足时 LLM 摘要）。

## 一、会不会降低模型性能？——不会，且三重缓解"压缩有损"

1. **常规轮零影响**：两个目录新 hook 均为"只读 + 静默"设计——未到阈值不输出；到阈值只注入"请模型转述"的软提醒，不阻塞、不改请求内容。
2. **提前预警替代漂移**：v2 学习线（deepseek 强档 ≈128K / 轻档 ≈88K；gpt ≈171K / ≈131K）让用户在**任务边界**获得一次主动选择（开新会话无损接手 / 主动 `/compact` 压得更干净）。
   - 回放对照（4 个真实会话，以代号表示，按 epoch 峰值）：sess-a v1/200K ≈2 次（均迟到失效）→ v2 学习线 ≈11 次准时；sess-b 6 次；sess-c 3 次（1 轻 2 强）；sess-d 0 次（峰值 122K 未达线）。
   - 频率有界：每次压缩纪元 ≤2 次（轻/强各一），无刷屏风险。
3. **压缩质量增强**：PreCompact 注入保留清单（任务目标 / 未决事项 / 关键决策 / 路径细节 / 用户偏好 / 教训），让摘要服务于"继续工作"而非复述对话。
4. **压缩后检查**：post >100K → 建议收尾换会话；实测本机 10 次压缩落点 36.7–100.4K（仅 1 次 >100K）。
5. 残余损失（声明）：压缩毕竟有损，摘要外细节不可恢复——细节关键的长任务按提醒优先"新会话 + 记忆衔接"。

## 二、成本降低幅度（token 口径量化）

样本：sess-a（deepseek，7 小时重型会话：518 次 API 请求 / 24 个用户轮次 / 10 次压缩）。  
方法：直读 transcript 的 `rawUsage.prompt_tokens` 序列；反事实 = 从未压缩（每轮按实测增量、中位 1,469 token 增长）。

| 指标            | 实测                                                                     |
| ------------- | ---------------------------------------------------------------------- |
| 单次压缩回收        | 48–190K，均值 **~106K**                                                   |
| 压缩后每轮输入瞬降     | 60%–75%（典型 183.4K → 48.6K）                                             |
| 压缩后落点（10 次）   | 48.6 / 60.0 / 81.0 / 88.3 / 36.7 / 48.2 / 66.8 / 78.3 / 93.3 / 100.4 K |
| 实际输入重放        | **65.6M** token（均值水位 127K/轮）                                           |
| 无压缩反事实        | 350.0M token                                                           |
| **节省（反事实口径）** | **284.4M token，-81%**                                                  |

- 口径说明：反事实世界会持续顶到窗口上限并频繁 emergency，物理上跑不完全程；-81% 的意义是"压缩让 518 请求的重放量保持在窗口内"。
- 金额折算：遵循“价格不写入产品”的项目原则，本文不披露任何金额数据；成本均以 token 口径呈现。
- v2 的增量（时机价值）：避免漂移。例：sess-a 第 5 次压缩发生在 226.4K（漂移 +76K）；v2 在 ~128K 即提醒，任务边界提前压缩每次可少处理 ~30–90K 历史。
- 对照：开新会话更省（回到 ~34K 固定前缀）但损失连续性——v2 的价值 = 把选择权在正确时点交给用户。

## 三、稳定性

1. **测试全绿（本机实测，2026-10-16 00:0x–00:2x）**，合计 398 项：

| 套件                | 结果          | 说明                                                                                        |
| ----------------- | ----------- | ----------------------------------------------------------------------------------------- |
| test_hook.py      | **29/29**   | 本次新增 10 项：v2 专项 7（学习/手动排除/学习线生效/压缩后告警与静默/pending 时序/env 覆盖/垃圾输入）+ PreCompact 3；5g 扩为四事件断言 |
| test_parity.py    | **46/46**   | 22/22 双实现逐字节一致 + 记账 12 + 预算 12                                                            |
| test_report.py    | **50/50**   | 含 demo/坏数据/prune/真实目录零写入                                                                  |
| test_stability.py | **273/273** | 边界 33 + fuzz 240；并发 32 任务、长跑 300 次；耗时 175.0s                                              |

1. 容错已测：空/垃圾 stdin、事件名不符、内部延续、缺 transcript、首条消息无 usage、非法 env、off 开关 → 全部静默退出码 0；状态文件损坏/旧格式（v1）自动重建。
2. 性能开销：每用户消息 1 次尾部读取（256KB 快路径；首见/压缩后 16MB 全读），交付实测常规 ~0.26s、全读 ~0.31s；hook 超时 5s 余量充足。
3. 已知边界（备查，非缺陷）：状态文件无锁（并发提交 last-writer-wins，最坏为偶发重复/漏一次提醒）；首条消息恒静默（无 usage 可读，设计使然）；学习样本夹紧 [100K, 2M]；软提醒依赖模型转述。
4. 回滚：`WB_OPS_CTX_GUARD=off` 即时静默；插件级回滚 = 注册表指回 0.5.0 快照（cache 保留）。

## 四、结论与观察项

- **性能**：不会降低；常规轮零感知，压缩路径<u>三重保护（早提醒 / 保留清单 / 重底子告警）。</u>
- **<u>成本</u>**<u>：单次压缩 ≈ 回收 106K token 重放；重型会话 -81%；日常长会话可按"每压缩一次 ≈ 后续每轮省 6–19 万 token 重放"感知。</u>
- **<u>稳定性</u>**<u>：398 项全绿、三层一致、实机运行正常；剩余风险仅为无锁状态的轻微非确定性（无阻塞/崩溃面）。</u>
- 观察项（可选调优）：deepseek 轻档 ~88K 偏早（一次性轻提醒）；若嫌频繁可调 `WB_OPS_CTX_GUARD_STEP`（加大档距）或 `WB_OPS_CTX_GUARD`（手动指定轻档线）。
- 维护注：本次把 v2 回归用例同步进三层快照（仅测试文件变更，不动运行时行为，未升版本）。

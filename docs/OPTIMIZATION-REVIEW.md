# wb-ops 优化评估：用另一平台同类插件的技术透镜再找一遍空间（→ v0.2.2）

- 日期：2026-10-15
- 前置：另一平台的同类插件全量审查
- 结论：**采纳 6 项可迁移技术，落地为 wb-ops v0.2.2**（已同步到安装快照，下个会话起生效）；
  2 项结构性不适用；1 项（WebFetch/WebSearch 覆盖）已预置探针待验。

## 1. 同类插件技术点 → wb-ops 映射

| # | 同类插件做法（出处） | wb-ops 旧状（0.2.1） | 0.2.2 落地 |
|---|---|---|---|
| 1 | **字节预算**：`max_bytes` 按字节计数（`results.rs`） | 按**码点**计 8000，中文内容 1 字=3 字节，可绕过上界约 3 倍 | 全链路按 UTF-8 **字节**：触发条件 / 总预算 / 单行切分 |
| 2 | **显式记账**：`complete` / `omitted` / `nextOffset`，让消费方知道丢了什么形状 | 标记只说"省略 N 行" | 标记显式化：抽样声明（"命中 42 条中均匀抽取 21 条"）、末尾段独立标记 |
| 3 | **有界但保真**：按整条记录给预算，不做半数切半 | 预算均摊到每行（8000/115≈69 字节/行），**实测 116/116 行全被截断** | 段内**整行优先**；放不下才截断"末行"一次；整段消耗不超配额 |
| 4 | **均匀抽样 / 窗口语义**：offset 分页，每页均匀 | 关键字超 40 条只取**最前面 40 条**（后段错误静默丢失） | 超上限按 `ceil(n/40)` 步长**均匀抽取**，覆盖前中后 |
| 5 | **envelope 预留**：为宿主附加内容预留 128 字节 | 标记不计入预算，结果实际略超 8000 | 标记预留 300 字节 + 兜底硬截断，结果**恒 ≤ 8000 字节** |
| 6 | **防无界内存**（其自身 P0：`read_bytes` 先读后检） | stdin 无上限读入 | `> 8MB` 直接透传 |
| 7 | 句柄级路径防护 / TOCTOU（`cap-std`） | — | **不适用**：wb-ops 只读 stdin、写 stdout，零文件系统操作 |
| 8 | 身份 / 作用域校验 | — | **不适用**：post-hoc 纯函数，无跨调用状态 |
| 9 | 测试纪律 | — | **反向输出**：wb-ops 有 20 用例逐字节一致性测试；对方 rust native/ 反而零测试 |

## 2. v0.2.2 改动明细

1. **字节预算**（`MAX_CHARS`→`MAX_BYTES=8000`，两实现同步）
   - 中文长行场景：43,094 字符输出 → 2,663 字符（≤8000 字节），不再有 3 倍级超支。
   - 长文本路径（行少字节多）上限 6000 → 7,400 字节，更贴近 8000。
2. **整行保真**（本次最大质量提升）
   - 3000 行真实 grep：0.2.1 = 116 行**全截断**；0.2.2 = 70 行中 **68 行完整**、仅 2 行截断。
   - 保底配额：关键字段 ≥30%、结尾段 ≥30%，前面段用不完的额度自动留给后面（头部 ≤40% 封顶）。
   - 结尾段按"从最后一行往前"填充，保证展示的就是原文末尾连续若干行。
3. **显式记账标记**（4 种，模型可自校准信任度）
   - `… [wb-ops 省略 2932 行，命中关键字的 42 条中均匀抽取 21 条如下] …`
   - `… [wb-ops 省略 N 行，以下为捞回的 M 条关键字行] …` / `… [wb-ops 省略 N 行，未发现 error/warning 关键字] …`
   - `… [wb-ops 以下为原文末尾 N 行] …`（结尾段独立标记，消除"末尾行伪装成关键字行"歧义）
4. **均匀抽样**：59 条命中 → 均匀 30 条，首尾命中均可见（测试断言 "err-0050" 与 "err-2950" 同时保留）。
5. **硬上界 + 输入护栏**：结果恒 ≤8000 字节（全局断言）；stdin >8MB 透传。
6. **运维修补**：节省基准脚本不再硬编码版本号（自动取最新快照）；`sync` 增加
   plugin.json/脚本 VERSION 一致性检查（防版本漂移）。

## 3. 实测

### 3.1 整行保真对照（本机真实 grep，3000 行 / 315,907 字节）

| | 输出字节 | 展示行数 | 其中截断行 | 备注 |
|---|---|---|---|---|
| 0.2.1 | 8,473 | 116 | **116（100%）** | 每行都被 69 字节均分预算切过 |
| 0.2.2 | 7,785 | 70 | **2（3%）** | 68 行完整；抽样声明 + 末尾标记 |

### 3.2 真实负载基准（5 场景）

| 场景 | 原始字符 | 0.2.1 | 0.2.2 | 0.2.2 省 |
|---|---|---|---|---|
| mingw 头文件搜索 3000 行 | 315,907 | 8,205 | 7,723 | 97.6% |
| 系统头文件清单 (Glob 式) | 100,555 | 4,334 | 4,360 | 95.7% |
| 插件配置 JSON 搜索 | 47,102 | 8,145 | 7,576 | 83.9% |
| JS 代码搜索（1 行长文本） | 18,700 | 6,026 | 7,426 | 60.3% |

- 合计节省持平（93.5%），但结构变了：截断从"每行都切"变为"整行连片 + 少量截断"。
- 长文本场景 0.2.2 多保留约 1,400 字节（原来的 6000 上限过于保守，现贴近 8000 硬上界）。
- jsonl 场景按字符看 5,625，按字节是 7,437（中文占位），**字节上界按设计生效**。

### 3.3 测试

- `test_parity.py`：**20/20 一致**（Python 版与原生版逐字节相同），含 3 个新增用例：
  整行保真（中等长度行完整保留）、关键字超 40 均匀抽样、全局字节上界断言。
- `test_hook.py`：3 场景全过（大输出裁剪+关键字、小输出透传、5 类畸形输入不崩）。

## 4. 结构性上限与未采纳项

- **Bash 输出**：宿主 `extractRawResponse` 不下发 stdout 正文（rawResponse 是沙箱元数据），
  PostToolUse 层面无解。这正是与同类插件的本质差别——对方自持执行层，可从源头限流；
  wb-ops 是纯后处理，只能处理宿主愿意下发的部分。*除非宿主后续修 payload，否则维持现状。*
- **Read**：维持不覆盖（整文件读取是刻意行为，截断会破坏编辑流程）。
- **展示行数下降**：整行保真的代价是行数变少（70 vs 116）。取舍已固化为"整行优先"；
  若更想要"行数覆盖"，改回 0.2.1 算法即可（见 §6）。

## 5. WebFetch / WebSearch 探针（已预置，待下次会话收割）

同类插件能在输出源头限流；wb-ops 能触达的最后一块未知疆域是 WebFetch/WebSearch —— 宿主是否把
正文下发给 hook 尚未验证。已预置探针（**仅作用于 cache 0.2.2 副本，开发目录未动**）：

1. `cache/.../0.2.2/hooks/hooks.json`：matcher 临时加宽为 `Grep|Glob|WebFetch|WebSearch`
2. `cache/.../0.2.2/bin/TRACE-ON`：trace 开关已放置

**收割步骤**：任意新会话中正常发生一次 WebFetch/WebSearch 调用后，查看
`~/.workbuddy/plugins/cache/local/wb-ops/0.2.2/bin/trace.log`，若出现

```
工具 WebFetch 不在裁剪名单，透传 | obj{content=str(N), ...}
```

即说明正文可达（N 为长度），再决定是否接入 0.2.3；若 `keys=` 里没有正文字段则维持不覆盖。

**收尾**：删除 `TRACE-ON` 即关闭跟踪；matcher 会被下一次 `sync` 自动还原（TRACE-ON 需手动删）。

## 6. 回滚路径

- 回滚 = 源文件回退后改 VERSION 重跑 `install_wb_ops.py sync`（或直接把旧快照内容拷回对应 cache 目录）
- cache 里多版本快照共存、互不影响；旧会话进程仍按其加载版本运行

### 7.3 待决策建议（未实施）—— 附 2026-10-15 量化评估

**结论先行：四项均无"性能（速度）"意义上的实质提升——唯一的速度项（④）只省 ~47ms，人眼无感。**
真正价值在信息面：③ 揭示成本结构、② 覆盖率 4.25 倍且精确、① 是可控性旋钮。建议顺序 ③ → ②（搭车 ④）→ ①。

**基准实测（2026-10-15 20:5x）**：报告核心管线 0.232s，其中两遍扫描 0.231s（99.6%），
聚合+渲染仅 0.001s；扫描细分：`scan_rid_ts`（局部 12 会话）0.058s + `scan_model_usage`（全量 51 文件）0.179s。

1. **`WB_OPS_BUDGET` 可配置**——非速度项，是"信息保留 vs token 花费"的旋钮。
   实测敏感性（基准 50,547 → 6,682，省 86.8%）：
   预算 4000 → 省率 93.4%（省量 +7.6%）；16000 → 省率 73.6%（省量 -15.2%，保留内容翻倍）；24000 → 省率 60.3%。
   要点：省率大头已由省略部分贡献，改预算主要影响"给模型读多少"；当前 8000 保留约 13% 内容。
2. **上下文区块全量化**——覆盖率 12 → 51 个会话（4.25 倍）。
   **实测修正：不是"近似"而是精确复原**——transcript 最后一轮 `prompt_tokens` 与宿主 `used` 6/6 完全相等
   （逐字一致，已验 98,853/34,920/136,839/150,810/200,046/34,601），宿主 used 即取自最后请求的 prompt_tokens。
   实现成本≈0（搭车 ③/④ 的扫描）。注意价值属性：窗口外均为已结束会话，属"历史复盘"而非"活跃预警"
   （活跃会话恒在最近 12 条内），故优先级中低、但搭车做极便宜。
3. **缓存命中统计**——数据覆盖 100%（2420/2420 行），三种格式可归一提取：
   DeepSeek `prompt_cache_hit_tokens/miss`（1895 行）、Anthropic `cache_read_input_tokens`（471 行）、
   OpenAI `cached_tokens`（54 行）。**全局实测缓存命中率 95.0%**（2.917 亿 / 3.071 亿）——
   报告中"按模型"的输入 token 是名义值，真实成本 95% 走缓存价；加列后成本理解从名义拉向真实。
   零额外扫描成本（与 model 扫描共用遍历）。**信息价值最高的一项，建议先做。**
4. **扫描合并**——唯一速度项：局部扫描 0.058s 并入全量后总扫描 ~0.185s，核心管线 0.232 → ~0.185s
   （-20%，绝对省 ~47ms，低于人眼 100ms 感知阈，用户无感）。真正理由：②③ 扩字段后两遍易变三遍，
   单遍架构更清晰；做 ②③ 时顺手合并即可。

### 7.4 积分机制破译与项 ⑤（2026-10-15 21:1x 追加）

**重大发现——宿主积分机制已完全破译**（为回答"插件能减少多少积分"而查明）：
`credit_json[轮id] = Σ 去重后全部 providerData.rawUsage.credit 记录`（宿主 JS 源码 `collectRequestCreditsFromHistory`
实证；三路闭合：15/15 rid 重建一致、sess-h 71.69=71.69、sess-a 差 0.00）。
单次调用计费公式（deepseek-v4.1-flash）：`0.573e-6×hit + 28.574e-6×miss + 114.426e-6×out`
（278 条全量拟合，误差中位 2%、合计偏差 0.0%）。

**裁剪的积分节省实测**：单次 43.9KB 超额裁剪在 126 次后续调用中省 1.11 分（本会话 3.0%）；
典型会话全程生效推演 1.27 分（1.8%）。**日常区间 1~3%**（真实工具输出最大仅 32KB、>8KB 仅 10%）。
计算模型：省 = 超额token × (miss价 + hit价 × 后续调用数)。500KB 输出在 100 调用中 ≈10.5 分。

**项 ⑤（升级版）**：报告可用 credit 记录**全量重建积分与真实成本**（按轮/按模型拆分，
突破 session_usage 12 行窗口；且与 ② 的扫描同源）。依赖：无（本轮已拿到公式与重建逻辑）。

### 7.5 实施记录与决策（2026-10-15 21:4x）

决策：**①②③④ 四项全部实施**；同时明确**价格/金额功能不进入产品**——
0.3.4 新增的"估算节省金额"（价目表换算）整体回退，报告不再引用任何价格数据。落地为 **0.3.5**：

- ① `WB_OPS_BUDGET` 可配置预算（trim.py + trim.cpp 双实现）：字节预算，默认 8000，
  范围 [2000, 131072]；非法值回退默认、越界收敛、容忍两端空白与前导零（纯 ASCII 数字解析）。
  实测（17.5KB 输入）：2000 → 1761B / 4000 → 3782B / 8000 → 5348B / 16000 → 6653B，单调可控；
  长文本路径首尾额度随预算等比缩放（默认 8000 → 5000/2400 与旧版逐字节一致）。
  test_parity 新增预算专项 12 项断言（双实现一致 + 边界收敛）。
- ② 上下文区块全量化：单遍扫描的 `ctx`（各会话末次请求 prompt_tokens）并入 usage_rows，
  实测覆盖 **12 → 47 个会话**（34 个窗口外由 transcript 补齐）；分母按同模型已知上下文窗口补齐，
  未知时只显示绝对数值（不假装有百分比）。
- ③ 缓存命中统计：三格式归一提炼 `hit`（DeepSeek hit / Anthropic cache_read / OpenAI cached_tokens），
  模型表新增"缓存命中 / 命中率"两列。实测全局 **95.2%**（deepseek 96.7% / gpt 88.9% /
  kimi 96.8% / glm 76.8% …）——名义输入 token 与真实计费之间的差距一目了然。
- ④ 扫描合并：`scan_rid_ts` + `scan_model_usage` + 上下文直读 三合一为 `scan_transcripts()`
  单遍产出 (models, rid_ts, ctx)。实测 51 文件 0.203~0.241s（原两遍 0.058+0.179≈0.237s），
  速度基本持平（省 ~20ms，人眼无感）；真正收益是**架构**：后续再扩字段不会变成三遍/四遍。

项 ⑤（真实成本区块）本轮**不采纳**：项目约定价格不写入后台，积分/成本口径保持宿主 credit 现状。
另：修复 test_stability 一条自 0.3.3 起过期的用例（WebFetch 已入裁剪名单，仍按"名单外透传"断言）。

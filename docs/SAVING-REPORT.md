# wb-ops 节约效果对比测试报告

版本：**0.2.1（原生 exe）** ｜ 最后更新：2026-10-15 17:20 ｜ 宿主：WorkBuddy 5.8.2

---

## 一、测试口径（为什么这个对比成立）

插件的作用是拦截工具输出、替换成裁剪版。所以：

- **原始** = hook 输入里 `tool_response` 的完整正文 —— 也就是 **不装插件**时模型会看到的内容
- **裁剪后** = hook 输出的 `updatedToolOutput` —— 也就是 **装了插件**后模型实际看到的内容

两者之差，就是插件带来的净节约。这不是估算，是同一份数据的两种去向。

token 估算规则：中日韩字符按 1 字 ≈ 1 token，其余按 4 字符 ≈ 1 token（英文/代码为主时的常用近似）。

## 二、真实链路端到端验证（最硬的证据）

造一个 500 行结果的文件，在**真实会话**里执行一次 Grep，然后三路交叉验证：

| 证据来源 | 数值 |
|---|---|
| hook 自身 trace 日志 | `工具 Grep 已裁剪：50050 -> 9957 字符` |
| 会话转录中模型实际收到的内容 | **9,957 字符 / 77 行** |
| 裁剪标记 | `… [wb-ops 省略 299 行，以下是其中 1 条命中关键字的行] …` |

**三者完全吻合** → 确认 9,957 字符就是最终进入上下文的全部内容，插件在真实链路上确实生效，不是自测幻觉。

| 指标 | 数值 |
|---|---|
| 原始 | 50,050 字符 |
| 裁剪后 | 9,957 字符 |
| **实际节约** | **80.1%** |
| 关键行捞回 | 第 250 行 `ERROR undefined reference to solve()` 带原始行号保留 ✓ |

**副产物发现**：Grep 工具自身有输出上限（本次实际只返回 373 行，而非文件全部 500 行），插件是在这个上限之上再裁一次。也就是说**插件的收益是在宿主已有截断的基础上叠加的**。

## 三、控制变量测试（8 个场景）

同一份 payload 分别走"不裁剪"和"裁剪"两条路：

| 场景 | 原始行 | 裁后行 | 原始 tok | 裁后 tok | 节约 |
|---|---|---|---|---|---|
| Grep 300 行纯匹配 | 300 | 76 | 7,098 | 1,787 | **74.8%** |
| Grep 400 行含 2 条关键行 | 400 | 78 | 9,473 | 1,836 | **80.6%** |
| Grep 800 行超大结果 | 800 | 77 | 18,974 | 1,814 | **90.4%** |
| Grep 中文日志 200 行 | 200 | 77 | 3,897 | 1,494 | **61.7%** |
| Glob 250 条路径 | 250 | 76 | 4,546 | 1,378 | **69.7%** |
| Grep 超长单行（20K 字符） | 1 | 3 | 5,000 | 1,510 | **69.8%** |
| Grep 长行 100 行 × 800 字符（0.2.1 新增覆盖） | 100 | 76 | 20,025 | 2,036 | **89.8%** |
| Grep 短输出 8 行 | 8 | 8 | 186 | 186 | 0%（透传） |
| Grep 20 行（临界） | 20 | 20 | 468 | 468 | 0%（透传） |

**读法**：

- 结果越大，节约率越高（800 行到 90.4%）—— 固定保留 50 头 + 25 尾 + 关键行，分母越大越划算
- **中文日志只有 61.7%** —— 中文 token 密度高，裁剪后仍保留的 77 行本身就"贵"。这是插件的固有下限
- **短输出原样透传**，不制造任何风险（阈值以下不动）

## 四、一次真实任务能省多少

以「Grep 400 行含关键行」为代表值，单次省 **7,637 tokens**：

| 场景 | 单轮节约 |
|---|---|
| 一次任务含 5 次搜索 | 38,185 tokens |
| 一次任务含 10 次搜索 | 76,370 tokens |
| 一次任务含 20 次搜索 | 152,740 tokens |

**上下文累积效应**（省下的内容不再被后续每轮重发）：

| 搜索次数 × 剩余轮数 | 累计节约 |
|---|---|
| 10 次 × 30 轮 | ≈ 2,291K tokens |
| 20 次 × 50 轮 | ≈ 7,637K tokens |

> ⚠️ 口径说明：上表是**理论上界**——按"每一轮的上下文里都少这 7,637 个 token"线性累加。实际会因自动压缩（约 92% 阈值）而打折。真实含义是："如果不装插件，一次重度搜索任务的上下文会明显更早触顶"。

## 五、一致性 & 性能

**功能一致性**：原生 exe vs Python 回退，**18/18 场景输出逐字节一致**。

**耗时**（模拟宿主真实调用形态 `bash -c "<命令>"`，裸 PATH，15 次均值）：

| 实现 | 单次耗时 |
|---|---|
| 原生 exe | **308 ms** |
| Python 版 | **515 ms** |
| 提速 | **约 40%** |

> ⚠️ 耗时波动大：同一台机器上多次测量落在 **203–308 ms** 区间（exe），受系统负载影响显著。稳定结论是"exe 比 Python 快约 40%"，绝对值请当作量级参考而非精确值。
>
> 剩余开销主要是 Git Bash 在 Windows 上模拟 fork 的固有代价，宿主用 bash 执行 hook 命令就绕不过去 —— **这条路已经到底了**。

## 六、成本与边界

| 项目 | 状态 |
|---|---|
| 每轮固定上下文开销 | **0 tokens**（hook 不进上下文） |
| 覆盖工具 | Grep / Glob |
| 裁剪后字符上界 | 0.2.1 起有保证：保留部分 ≤ 约 8.1K 字符（长行场景不再失效） |
| Bash 输出裁剪 | ✗ 宿主 5.8.2 不下发 stdout 正文给 hook（宿主的缺陷，非配置问题） |
| 误裁风险 | 低（认不出结构就透传；短输出不动；异常静默退出） |
| 单次延迟成本 | 约 0.2–0.3 秒/次（仅 Grep/Glob，不影响 Bash） |

**净结论**：用每次 Grep/Glob 约 0.3 秒的延迟，换取该次输出 60–90% 的 token 削减。搜索越多、结果越大，这笔交易越划算。

## 八、真实使用回放与真实负载（17:20 补测）

### 8.1 实测验证：0.2.1 已实际接管

探针法实测（可复用的诊断手段）：在插件目录放一个空的 `bin/TRACE-ON`（调试开关），
发一次真实 Grep（130 行输出），然后看 trace 落在哪：

| 证据 | 结果 |
|---|---|
| trace 落点 | `cache/local/wb-ops/0.2.1/bin/trace.log`（17:12:02 写入） |
| 本次裁剪 | `工具 Grep 已裁剪：8582 -> 4907 字符`（130 行 → 75 行 + 省略标记，省 42.8%） |
| 探针清理 | 验证后已删除（残留 0 个，恢复零开销） |

**版本生效机制（本次实测修正）**：按**会话进程**粒度生效——install 之后新开的会话进程自动加载
0.2.1（本次 trace 落在 0.2.1 目录）；更早打开的会话进程仍走 0.2.0（16:52 的 trace 仍写在 0.2.0 目录）。
**不需要重启整个 WorkBuddy**，重开/新开会话即可。
